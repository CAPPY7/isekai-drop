# Code audit (Phase 7, 16 Oct 2026)

How: I read every engine, storage, platform and UI file (lib/, android MainActivity.kt, the iOS/macOS Swift files) and looked for crashes, broken features and security holes. Evidence is file:line at commit 9fcf2c7. "Probe" means I ran a throwaway test to confirm the bug.
Severity: **Crash** / **Security** / **Broken feature** / **Minor**.
Rule for this phase: only Crash and Security items may be fixed now, each in its own small commit with a test. Broken and Minor items wait for the owner.

| # | Severity | Problem | Evidence | Status |
|---|---|---|---|---|
| 1 | Security | **Discovery spoofing could block a trusted device and change its saved address.** Discovery messages are not authenticated. Anyone on the network could announce "I am device X with key K" from their own address. (a) The engine saved that address for X (`rememberAddress`). (b) The next send went there, TLS saw the wrong key, and the engine **permanently** marked X "identity changed" (blocked). Result: an outsider could block your trusted devices and redirect sends to themselves. No data leaked, because TLS refused the connection. | engine.dart:323 (address saved from an unauthenticated announcement), engine.dart:860 (always marks blocked), files_screen.dart:116 (uses the announced address) | FIXED: test "spoofed announcement neither blocks nor redirects" |
| 2 | Security | **Pairing request flood.** Any unknown device could open unlimited pairing requests. Each one queues a dialog for 2 minutes, so the screen could be filled with prompts (annoyance, and a risk of approving the wrong one by mistake). | engine.dart:455 `_ask(req)` with no limit; engine.dart:332 `_pending.add` | FIXED: test "a second pairing request while one is open is refused" |
| 3 | Security (accepted risk, disclosed) | If secure storage fails, the device's private key goes into `identity_fallback.json` (mode 600, app folder) and stays there ("sticky"), even if secure storage works later. This is needed on Linux without a keyring, and the app shows a note. | platform_engine.dart:37 | NOT fixed: owner decision needed (move the key back into secure storage when it becomes available?) |
| 4 | Security (low) | No limit on simultaneous incoming connections. Each unauthenticated socket may stay open up to ~45 s (TLS 15 s + first message 30 s), so a local attacker can use up resources. | engine.dart:271 `_server!.listen(_onIncoming)` with no cap | NOT fixed (low; proposal: cap at about 32 sessions) |
| 5 | Broken feature | **One damaged entry in trusted_devices.json loses ALL trusted devices.** `load()` throws on the first bad entry. The app then starts with an empty list, and the next pairing overwrites the file. | trust_store.dart:114; platform_engine.dart:136. Probe: file with 2 good + 1 damaged entry: load threw `_TypeError`, 0 devices kept, after the next pairing the file held 1 device. | NOT fixed (waits for OK). Proposal: skip bad entries and keep a .bak copy. |
| 6 | Broken feature | Android 9 and older: received files go to the app's own folder (Android/data/.../Download/Isekai Drop). The app says "Downloads/Isekai Drop", and that folder is removed if the app is uninstalled. | MainActivity.kt:228, :331; platform_engine.dart:177 | NOT fixed |
| 7 | Broken feature | The approval dialog stays open after the 2-minute timeout. Tapping Accept then does nothing and shows no message. | shell.dart:171 `if (r.decided) return;` | NOT fixed |
| 8 | Broken feature | Turning off "Visible to nearby devices" also stops Bonjour **browsing**, so this device finds fewer others (UDP still works). | platform_engine.dart:515 | NOT fixed (documented) |
| 9 | Broken feature | After the sender app restarts, failed sends have no Retry button. Resume still works, but only by picking the same files again. | jobs are in memory only (engine.dart `_jobs`) | NOT fixed (documented) |
| 10 | Minor (performance) | TLS, SHA-256 and file I/O all run on the UI isolate. Measured on the box (loopback, 1 GiB): 17.5 MB/s, CPU-bound. Large transfers may make the UI lag on slow phones. | engine.dart:680 (hash on the receive path), the send loop | NOT fixed: Phase 8 optimisation (move to a background isolate), measure first |
| 11 | Minor | Home shows raw state words ("running", "failed"). | home_screen.dart:112 | NOT fixed |
| 12 | Minor | Bonjour names are shortened but not cleaned of control characters (they are only displayed). | bonjour.dart:105 | NOT fixed |
| 13 | Minor | Leftover DEMO widgets (`DemoBanner`, `DemoChip`) are no longer used. | common.dart:8 | NOT fixed (removing code waits for OK) |
| 14 | Minor | Resume id = file names + sizes. A different file with the same name and size gives one failed attempt (the hash check catches it); the next retry starts fresh. | engine.dart `transferIdFor` | Known, documented |
| 15 | Minor | Android keeps partial files in the cache folder, which the system can clear. Resume then starts from 0. | platform_engine.dart:150 | Known, documented |
| 17 | Crash (uncaught async error) | Found while fixing #1: two trust-store saves at the same time both wrote `trusted_devices.json.tmp`. One rename then failed with PathNotFoundException as an **uncaught** error (seen as a flaky test failure, 1 in ~4 full runs). Fire-and-forget saves (address updates) made it possible. | trust_store.dart `_save` (no serialisation); engine.dart (unawaited `rememberAddress`) | FIXED: test "many saves at the same time do not race" fails before the fix, passes after |
| 16 | Minor | No free-space check before accepting. A full disk shows up as a generic "transfer stopped". | engine.dart `_serverReceive` | NOT fixed |

Crashes: apart from #17, I found **no crash** by reading or by the probes (all network input is parsed inside try/catch). One crash-class bug was found and fixed in Phase 6 (broken pipe surfacing as an uncaught error). This is not proof that there are no crashes: on-device testing has not been done.
