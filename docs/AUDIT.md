# Code audit (Phase 7, 16 Oct 2026)

How: I read every engine, storage, platform and UI file (lib/, android MainActivity.kt, the iOS/macOS Swift files) and looked for crashes, broken features and security holes. Evidence is file:line at commit 9fcf2c7. "Probe" means I ran a throwaway test to confirm the bug.
Severity: **Crash** / **Security** / **Broken feature** / **Minor**.
Rule for this phase: only Crash and Security items may be fixed now, each in its own small commit with a test. Broken and Minor items wait for the owner.

| # | Severity | Problem | Evidence | Status |
|---|---|---|---|---|
| 1 | Security | **Discovery spoofing could block a trusted device and change its saved address.** Discovery messages are not authenticated. Anyone on the network could announce "I am device X with key K" from their own address. (a) The engine saved that address for X (`rememberAddress`). (b) The next send went there, TLS saw the wrong key, and the engine **permanently** marked X "identity changed" (blocked). Result: an outsider could block your trusted devices and redirect sends to themselves. No data leaked, because TLS refused the connection. | engine.dart:323 (address saved from an unauthenticated announcement), engine.dart:860 (always marks blocked), files_screen.dart:116 (uses the announced address) | FIXED: test "spoofed announcement neither blocks nor redirects" |
| 2 | Security | **Pairing request flood.** Any unknown device could open unlimited pairing requests. Each one queues a dialog for 2 minutes, so the screen could be filled with prompts (annoyance, and a risk of approving the wrong one by mistake). | engine.dart:455 `_ask(req)` with no limit; engine.dart:332 `_pending.add` | FIXED: test "a second pairing request while one is open is refused" |
| 3 | Security (accepted risk, disclosed) | If secure storage fails, the device's private key goes into `identity_fallback.json` (mode 600, app folder) and stays there ("sticky"), even if secure storage works later.
